Harness-agnostic agent tools and the human handoff

A manifest-first tool catalog, plus a containerized browser runtime whose handoff call puts a person in the loop through noVNC whenever an agent hits a login wall.

Built in 2026 · Part of my AI developer tooling work

Problem and constraints

I run several agent harnesses, local and in the cloud. Each has its own way to declare tools, and every one eventually reaches a single sign-on page it can't get past. I wanted one tool definition that every harness could use, and a safe way for a person to step in.

  • Tools must be described once and work in any harness.
  • Agents shouldn't load every tool schema up front, because it wastes context.
  • Credentials are never stored in the repo, and manifests name them without holding values.
  • A human handoff must always clean up after itself, even on a timeout.

Architecture

flowchart TD
  IDX[Catalog index] --> MF[Browser tool manifests]
  SCH[Schema contract] -.validates.-> MF
  MF -->|loaded at startup| RT[Browser runtime: MCP]
  H[Local and cloud harnesses] --> RT
  RT --> CT[Container: display + Chromium]

The repo holds manifests, not implementations. Level one is an index of namespaces, each with one line of description. Level two is one manifest per tool. An agent reads the index first and loads a namespace's schemas only when it needs them.

Every manifest follows one schema with no extra fields allowed. It requires a qualified name, a semver version, when to use the tool, typed inputs and outputs, a non-empty side-effect statement ("None." for read-only tools), named error codes, and the names of the credentials it needs. A checker validates every manifest against the schema. Policy and judgment stay in skills, not in tools.

The browser runtime reads its tool names, descriptions, and schemas from those manifests when it starts, so the contract and the server can't drift apart. Each harness starts the runtime in a Podman container with a virtual display and a persistent browser profile.

Control flow: one blocking handoff call

sequenceDiagram
  participant A as Agent
  participant R as Browser runtime
  participant N as Notifier
  participant P as Person
  A->>R: navigate, read
  R-->>A: login wall
  A->>R: handoff(reason, timeout)
  R->>R: start VNC + noVNC on free ports
  R->>N: POST reason, url, expires_at
  N->>P: notification with link
  P->>R: signs in on the same live browser
  P->>R: presses Done
  R->>R: stop VNC + noVNC
  R-->>A: done / timeout / cancelled
  A->>R: read (now signed in)

Handoff is one blocking call, not a start and stop pair. The runtime starts the screen share only for the length of the call, notifies me through a webhook, waits for Done, Cancel, or the timeout, and always tears the share down before it returns. The agent can't forget to stop sharing, because it never started sharing itself.

Data flow

  • In: tool calls from the harness over stdio. The settings are environment variables: profile directory, notify webhook, ports, and bind address.
  • Out to a person: one JSON message with the reason, a link, and an expiry. The link opens noVNC on the same live browser the agent was using.
  • Kept: only the browser profile, so a sign-in lasts across sessions. Handoff tokens and the X authority file sit in a runtime folder next to it.

Failure modes and guardrails

  • Notifier unreachable: handoff returns notify_failed and tears down the share. It never leaves a live screen open with nobody told.
  • Exposure: by default listeners bind to localhost, and the VNC server itself stays on a private localhost port.
  • Display collisions: the runtime picks a free display and never attaches to one in use.
  • Breaking changes: semver rules define when a contract change needs a major version bump.
  • Known gap: some harness launchers pin fixed ports, so a second parallel session can fail its handshake while the first holds them. The fix is per-session free ports in the launcher, which the runtime already supports.

Tradeoffs and alternatives I rejected

  • Driving my desktop browser over its debug port. It shares my real session, but a browser update or relaunch breaks it, and the agent gets my whole profile. The container keeps a separate profile and comes back on its own.
  • Separate start and stop handoff tools. A missed stop leaves a screen share open.
  • Tools defined per harness. Quicker the first time, but every harness then needs its own copy and they drift.

What I'd do next

  • Pick ports per session in every launcher, and add a health check before the first tool call.
  • Add more namespaces, such as chat, behind the same contract.

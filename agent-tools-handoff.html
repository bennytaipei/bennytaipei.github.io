Agent tool manifests and the browser handoff

I built a tool catalog where each tool is a manifest that any agent harness can load, and a containerized browser runtime with a handoff call that lets me sign in over noVNC when an agent hits a login page.

Built in 2026 · Part of my AI developer tooling work

Problem and constraints

I use several agent harnesses, local and in the cloud. Each declares tools differently, and each one eventually hits a single sign-on page it can't get past. I wanted one tool definition that works in every harness, and a way for me to sign in for the agent.

  • Each tool is described once and works in any harness.
  • Agents shouldn't load every tool schema at the start, because the schemas use up context.
  • The repo never stores credentials. Manifests name them without holding values.
  • A handoff must always stop sharing the screen, including on a timeout.

Architecture

flowchart TD
  IDX[Catalog index] --> MF[Browser tool manifests]
  SCH[Schema contract] -.validates.-> MF
  MF -->|loaded at startup| RT[Browser runtime: MCP]
  H[Local and cloud harnesses] --> RT
  RT --> CT[Container: display + Chromium]

The repo holds manifests, not implementations. The first level is an index of namespaces, each with a one-line description. The second level is one manifest per tool. An agent reads the index first and loads a namespace's schemas only when it needs them.

Every manifest follows one schema that allows no extra fields. It requires a qualified name, a semver version, when to use the tool, typed inputs and outputs, a side-effect statement ("None." for read-only tools), named error codes, and the names of the credentials it needs. A checker validates every manifest against the schema. Policy and judgment stay in skills.

The browser runtime loads its tool names, descriptions, and schemas from the manifests at startup, so the server always matches the contract. Each harness starts the runtime in a Podman container with a virtual display and a persistent browser profile.

Handoff control flow

sequenceDiagram
  participant A as Agent
  participant R as Browser runtime
  participant N as Notifier
  participant P as Person
  A->>R: navigate, read
  R-->>A: login wall
  A->>R: handoff(reason, timeout)
  R->>R: start VNC + noVNC on free ports
  R->>N: POST reason, url, expires_at
  N->>P: notification with link
  P->>R: signs in on the same live browser
  P->>R: presses Done
  R->>R: stop VNC + noVNC
  R-->>A: done / timeout / cancelled
  A->>R: read (now signed in)

Handoff is one blocking call. The runtime starts the screen share for the length of the call, notifies me through a webhook, and waits for Done, Cancel, or the timeout. It stops the share before it returns, so the agent never has to.

Data flow

  • The harness sends tool calls over stdio. Settings come from environment variables: the profile directory, notify webhook, ports, and bind address.
  • When a handoff starts, the runtime sends one JSON message with the reason, a link, and an expiry time. The link opens noVNC on the browser the agent was using.
  • Only the browser profile persists, so a sign-in carries over to later sessions. Handoff tokens and the X authority file are stored in a runtime folder next to it.

Failure modes and guardrails

FailureGuardrail
The notifier is unreachableHandoff returns notify_failed and stops the share, so a screen is never shared without a notification.
Network exposureListeners bind to localhost by default, and the VNC server stays on a private localhost port.
Display collisionsThe runtime picks a free display and never attaches to one in use.
Breaking contract changesSemver rules define when a change needs a major version.
Port conflicts between parallel sessionsSome launchers pin fixed ports, so a second session can fail its handshake while the first holds them. This is a known gap. The runtime already supports free ports, and the launchers need to use them.

Tradeoffs and alternatives

  • Driving my desktop browser over its debug port would share my real session. A browser update or relaunch breaks that connection, and the agent would get my whole profile. The container has its own profile and restarts on its own.
  • Separate start and stop handoff tools would leave the screen shared if the agent missed the stop call.
  • Defining tools per harness is faster the first time, but each harness then keeps its own copy and the copies drift.

Next steps

  • Use per-session ports in every launcher, and add a health check before the first tool call.
  • Add more namespaces, such as chat, under the same contract.

The devkit's ticket-to-PR agent pipeline

I built the devkit's pipeline. It splits a ticket into spec stories, runs each story through developer, tester, and PR-creator agents in a durable workflow, and builds each agent's prompt from a shared knowledge base.

Built in 2026 · Part of my AI developer tooling work

Problem and constraints

Engineers on a network-security product wanted coding agents to take routine stories from ticket to pull request without someone watching each run. One story takes 20 to 60 minutes of agent work. In-harness subagents expire and have no retry, so a long run could stop partway through without anyone noticing.

  • Many stories had to run in parallel, and one failure couldn't stop the rest.
  • Agents needed the team's build, test, and review knowledge.
  • Every engineer had to run the same version of that knowledge, updated with one command.
  • Credentials for background workers couldn't leak into interactive sessions.

Architecture

flowchart TD
  T[Ticket] --> B[Spec breakdown skill]
  B --> S1[Story 1]
  B --> S2[Story 2]
  B --> S3[Story N]
  S1 & S2 & S3 --> Q[Durable workflow queue]
  Q --> W[Story workflow]
  W --> D[Developer agent]
  D --> Te[Tester agent]
  Te --> P[PR-creator agent]
  P --> PR[Pull request on a product repo]
  KB[(Shared knowledge base)] --> X[Extract step]
  X --> R[Roles]
  X --> F[Workflows]
  X --> K[Facts]
  R & F & K --> W

The devkit is a plugin for a coding-agent harness. A breakdown skill splits a ticket into spec stories. A batch skill fetches all of them in one query, starts one Temporal workflow per story on a local server, and returns. A background worker picks up the workflows. In each one, the developer, tester, and PR-creator agents run in order, and each waits for the one before it.

Engineers can instead send the same stories to a shared, centrally run agent platform, one pipeline run per story. They choose local or shared execution per batch.

How an agent's prompt is built

flowchart TD
  A[Personal dev notes] --> E[Extract and classify]
  B[(Shared knowledge base)] --> E
  E --> R[Role]
  E --> F[Workflow]
  E --> K[Knowledge]
  R & F & K --> SP[Agent system prompt]
  G[Glossary + cited summaries] --> SP

The extract step sorts knowledge into three domains. Role lines are imperatives such as "always" and "never". Workflow lines are numbered steps and "when X" procedures. Knowledge lines are facts such as file paths, commands, ports, and conventions. Each agent's system prompt is its role, the selected workflow, and the relevant facts, followed by an optional glossary and cited summaries.

I kept role and workflow separate. A developer and a tester can both have a bug-handling workflow and still approach it differently. Keeping them apart lets the prompt builder combine any role with any workflow.

Engineers capture a decision locally. A conflict check runs against the shared base, and the entry goes in through a pull request that a knowledge-base owner reviews. After merge, the devkit's update command pulls it down and reseeds every project. The devkit only reads the shared base, and one separate plugin owns every write. Control flow

sequenceDiagram
  participant E as Engineer
  participant B as Batch skill
  participant Q as Workflow server
  participant C as Classifier (small model)
  participant A as Agents (main model)
  E->>B: run batch for stories
  B->>Q: start one workflow per story
  B-->>E: returns immediately
  Q->>C: ticket type, summary, description
  C-->>Q: new-requirement / bug / test-failure / pr-review
  Q->>A: developer (role + workflow + facts)
  A-->>Q: change ready
  Q->>A: tester
  A-->>Q: pass
  Q->>A: PR creator
  A-->>Q: PR opened

Before the agents run, a small model picks the workflow type from the ticket's type, summary, and the start of its description. It runs at temperature 0 and returns one word. This is a routing decision, so it doesn't need the large model. I chose this over keyword matching because keywords misroute without any error. "Address the erratic behavior in the auth module" is a bug with no trigger words, and "test the new login requirement" contains "test" but isn't a test failure. If the classifier call fails, the workflow uses new-requirement and continues.

Failure modes and guardrails

FailureGuardrail
An agent activity crashes or the API is briefly unavailableEach activity retries twice with a 30-second backoff. Workflow history survives machine restarts.
One story failsEach story is its own workflow, so the others keep running.
The tester never passesThe PR creator waits for a tester pass, so failing work doesn't become a PR.
The classifier is downThe workflow defaults to new-requirement.
The worker token leaks into interactive sessionsThe token lives in an env file that only the worker loads, not in the harness's shared settings.
Ticket fetches fill the context windowA script returns compact, field-filtered JSON instead of full tool responses.
Engineers run old knowledgeOne update command pulls the newest plugin and knowledge base and reseeds each project. A session-start hook checks freshness and suggests the command to run. It doesn't change files.

Tradeoffs and alternatives

  • Background subagents would be simpler, but they expire, have no retry, and can't run many hour-long stories in parallel. Temporal adds a daemon to install. In return it gives durable execution, parallel child workflows, and a UI for watching runs.
  • Two knowledge domains would mean fewer files, but role and procedure would be mixed together.
  • Running classification on the large model costs more and takes longer for a one-word answer.
  • Keeping a shared-platform path lets teams move work off laptops without rewriting stories.

Next steps

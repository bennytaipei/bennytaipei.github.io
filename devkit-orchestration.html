From ticket to pull request: the devkit's agent pipeline

How the devkit turns a ticket into small spec stories, runs each one through durable developer, tester, and PR-creator agents, and builds every agent's prompt from a shared knowledge base.

Built in 2026 · Part of my AI developer tooling work

Problem and constraints

Engineers on a network-security product wanted coding agents to carry routine stories from ticket to pull request without someone watching each one. A single autonomous story takes 20 to 60 minutes of agent work. In-harness subagents expire and have no retry, so a long run could fail silently partway through.

  • Many stories had to run in parallel, and one failure couldn't take down the rest.
  • Agents needed the team's real build, test, and review knowledge, not generic advice.
  • Every engineer had to run the same version of that knowledge, updated with one command.
  • Credentials for background workers couldn't leak into interactive sessions.

Architecture

flowchart TD
  T[Ticket] --> B[Spec breakdown skill]
  B --> S1[Story 1]
  B --> S2[Story 2]
  B --> S3[Story N]
  S1 & S2 & S3 --> Q[Durable workflow queue]
  Q --> W[Story workflow]
  W --> D[Developer agent]
  D --> Te[Tester agent]
  Te --> P[PR-creator agent]
  P --> PR[Pull request on a product repo]
  KB[(Shared knowledge base)] --> X[Extract step]
  X --> R[Roles]
  X --> F[Workflows]
  X --> K[Facts]
  R & F & K --> W

The devkit is a plugin for a coding-agent harness. A breakdown skill splits a ticket into spec stories. A batch skill fetches all of them in one query and starts one durable workflow per story on a local Temporal server, then returns at once. A background worker picks the workflows up. Inside each one, three agents run in order: developer, then tester, then PR creator. Each step waits for the one before it.

The same stories can instead be sent to a shared, centrally run agent platform, one pipeline run per story. Engineers pick local or shared execution per batch.

Data flow: how an agent's prompt is built

flowchart TD
  A[Personal dev notes] --> E[Extract and classify]
  B[(Shared knowledge base)] --> E
  E --> R[Role]
  E --> F[Workflow]
  E --> K[Knowledge]
  R & F & K --> SP[Agent system prompt]
  G[Glossary + cited summaries] --> SP

The extract step sorts knowledge into three domains. Role lines are imperatives such as "always" and "never". Workflow lines are numbered steps and "when X" procedures. Knowledge lines are facts: file paths, commands, ports, conventions. Each agent's system prompt is role plus the selected workflow plus the relevant facts, then an optional glossary and cited summaries.

I kept role and workflow apart on purpose. A developer and a tester can both have a "handle a bug" workflow but look at it through different lenses. Merging them would blur identity and procedure, and the prompt composer couldn't mix them freely.

The knowledge base has a strict boundary. Engineers capture a decision locally, a conflict check runs against the shared base, and the entry goes in through a pull request that a knowledge-base owner reviews. After merge, the devkit's update command pulls it down and reseeds every project. The devkit only reads the shared base. One separate plugin owns every write. The kit overview has the sync diagram.

Control and logic flow

sequenceDiagram
  participant E as Engineer
  participant B as Batch skill
  participant Q as Workflow server
  participant C as Classifier (small model)
  participant A as Agents (main model)
  E->>B: run batch for stories
  B->>Q: start one workflow per story
  B-->>E: returns immediately
  Q->>C: ticket type, summary, description
  C-->>Q: new-requirement / bug / test-failure / pr-review
  Q->>A: developer (role + workflow + facts)
  A-->>Q: change ready
  Q->>A: tester
  A-->>Q: pass
  Q->>A: PR creator
  A-->>Q: PR opened

Before the agents run, a small, fast model picks the workflow scenario from the ticket's type, summary, and the start of its description, at temperature 0 with a one-word answer. That is a routing decision, so it doesn't need the large model. I rejected keyword matching because it fails quietly: "address the erratic behavior in the auth module" is a bug with no trigger words, and "test the new login requirement" contains "test" but isn't a test failure. If the classifier call fails, the workflow falls back to new-requirement and keeps going.

Failure modes and guardrails

FailureGuardrail
Agent activity crashes or the API is briefly unavailableEach activity retries twice with a 30-second backoff. Workflow history survives machine restarts.
One story failsEach story is its own workflow, so the rest keep running.
Tester never passesThe PR creator waits for a tester pass, so failing work never becomes a PR.
Classifier is downDefaults to new-requirement instead of blocking.
Worker token leaks into interactive sessionsThe worker's token lives in its own env file that only the worker loads, never in the harness's shared settings.
Ticket fetches flood the context windowA script returns compact, field-filtered JSON instead of large tool responses.
Engineers drift onto old knowledgeOne update command pulls the newest plugin and knowledge base and reseeds each project. A session-start hook checks freshness and suggests the command to run, but never changes files on its own.

Tradeoffs and alternatives I rejected

  • Background subagents instead of a workflow engine. Simpler, but they expire, have no retry, and can't run many hour-long stories in parallel. Temporal adds a daemon to install, and in exchange I get durable execution, parallel child workflows, and a UI for watching runs.
  • Two knowledge domains instead of three. Fewer files, but role and procedure get tangled.
  • One large model for everything. Classification on the big model costs more and is slower, with no accuracy gain on a single-token answer.
  • Local-only execution. Keeping a shared-platform path lets teams move work off laptops without rewriting stories.

What I'd do next

  • Add an evaluation set of past stories so changes to prompts and knowledge can be scored before rollout.
  • Record classifier decisions next to outcomes, to see which scenarios get misrouted.
  • Track per-story cost and time so we can decide which stories should go local and which should go to the shared platform.

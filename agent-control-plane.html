Running many coding agents at once: a lightweight control plane

How I keep track of parallel coding-agent sessions across harnesses with per-agent status files, a census, and clean handoff rules, without a central server.

Built in 2026 · Part of my AI developer tooling work

Problem and constraints

On a busy day I have several coding agents running in parallel, in different harnesses, repos, and worktrees. Questions kept coming up: which session owns which task, which one is blocked on me, and where a new session should pick up when an old one runs out of context. Asking each session took time and cut into its work.

  • It had to work the same way in every harness.
  • There could be no shared file that two agents write at once.
  • A successor session had to be able to resume from what's on disk alone.
  • It could add almost no load to me.

Architecture

flowchart LR
  A1[Agent, harness 1] -->|atomic write| S1[agent-A.json]
  A2[Agent, harness 2] -->|atomic write| S2[agent-B.json]
  A3[Agent, harness 3] -->|atomic write| S3[agent-C.json]
  S1 & S2 & S3 -->|read only| C[Census]
  L[Session control server] --> C
  C --> V[One view: task, state, blocked, needs me]

Every harness gets the same rule text, kept in one canonical file. Each agent writes only its own status file, named by harness and session id, in an ignored folder at the project root. The census reads those files to show one view of what's running. Session listing and steering go through local-agent-mcp.

Data flow: the status record

GroupFields
Identityharness, session id, pid, census slot
Task treetask key, parent, children, replaces
Locationbranch, worktree, PR links
Stateactive, blocked, parked, done, exited, plus replaced and split for handoffs
Progressdoing, next, checkpoint (what's done, where, and the exact next step)
Attentionblocked, needs_human, health, context_near_limit, updated_at

Each agent writes atomically: it writes to a temp file in the same folder, then renames it onto its own file. Readers never see half a record.

Control and logic flow

flowchart TD
  S([Session starts]) --> L[List status files]
  L --> N{Task named by me?}
  N -->|yes| R[Read newest file for that task, resume from checkpoint]
  N -->|no| O{Open files exist?}
  O -->|yes| Q[Ask once which one to continue]
  O -->|no| NEW[Start a new file]
  R --> M[Mark old file replaced]
  Q --> M
  M --> W[Work and write at milestones]
  NEW --> W
  W --> SP{Split?}
  SP -->|yes| CH[Children A-1, A-2, each with its own worktree. Parent marked split]
  SP -->|no| E([Exit: done, parked, or exited, with a checkpoint])

Agents write at startup, at milestones (plan set, blocked, PR opened, handoff), whenever state or needs_human changes, and on exit. The startup question is the only interruption allowed under my Keep-Going anti-stall rules, and the agent asks it only when the choice is truly ambiguous.

Failure modes and guardrails

  • Write collisions: one file per agent, written atomically. Agents never edit each other's files, except to mark a file whose process is gone or when I ask.
  • Lost context: the checkpoint field is written for a stranger to resume from.
  • Parallel edits to the same files: each split child gets its own worktree and branch. The default is one seat per initiative.
  • Leaking into the repo: the folder is added to git's local exclude list and never committed.
  • Stale census: the census marks sessions with no live process as not live instead of trusting their last report.

Tradeoffs and alternatives I rejected

  • A single shared status file. I started with one. I moved to per-agent files so concurrent writers can never overwrite each other.
  • A central server or database. More features, but one more thing to keep alive, and every harness would need a client. Plain files work everywhere.
  • Asking each session for status. Costs every session context and attention. Reading a file costs it nothing.

What I'd do next

  • Publish the status schema as a JSON Schema and validate files on write.
  • Add a small dashboard on top of the census for blocked and needs-human items.

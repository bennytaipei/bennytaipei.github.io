Tracking parallel coding-agent sessions

I led the design of the status rules I use to track parallel coding-agent sessions across harnesses. Each agent writes its own status file, a census reads them, and handoff rules let a new session resume from disk. There is no central server.

Built in 2026 · Part of my AI developer tooling work

Problem and constraints

I often run several coding agents at once, in different harnesses, repos, and worktrees. I needed to know which session owns which task, which one is waiting on me, and where a new session should resume when an old one runs out of context. Asking each session took time and interrupted its work.

  • It had to work the same way in every harness.
  • Two agents couldn't write to the same file.
  • A new session had to be able to resume from what's on disk.
  • It had to need very little attention from me.

Architecture

flowchart LR
  A1[Agent, harness 1] -->|atomic write| S1[agent-A.json]
  A2[Agent, harness 2] -->|atomic write| S2[agent-B.json]
  A3[Agent, harness 3] -->|atomic write| S3[agent-C.json]
  S1 & S2 & S3 -->|read only| C[Census]
  L[Session control server] --> C
  C --> V[One view: task, state, blocked, needs me]

Every harness gets the same rule text from one canonical file. Each agent writes only its own status file, named by harness and session id, in an ignored folder at the project root. The census reads those files and shows what's running. Session listing and steering go through local-agent-mcp.

The status record

GroupFields
Identityharness, session id, pid, census slot
Task treetask key, parent, children, replaces
Locationbranch, worktree, PR links
Stateactive, blocked, parked, done, exited, plus replaced and split for handoffs
Progressdoing, next, checkpoint (what's done, where, and the exact next step)
Attentionblocked, needs_human, health, context_near_limit, updated_at

Each agent writes to a temp file in the same folder, then renames it onto its own file, so readers never see a partial record.

Session lifecycle

flowchart TD
  S([Session starts]) --> L[List status files]
  L --> N{Task named by me?}
  N -->|yes| R[Read newest file for that task, resume from checkpoint]
  N -->|no| O{Open files exist?}
  O -->|yes| Q[Ask once which one to continue]
  O -->|no| NEW[Start a new file]
  R --> M[Mark old file replaced]
  Q --> M
  M --> W[Work and write at milestones]
  NEW --> W
  W --> SP{Split?}
  SP -->|yes| CH[Children A-1, A-2, each with its own worktree. Parent marked split]
  SP -->|no| E([Exit: done, parked, or exited, with a checkpoint])

Agents write their file at startup, at milestones such as setting a plan, getting blocked, opening a PR, or handing off, whenever state or needs_human changes, and on exit. The startup question is the only interruption my Keep-Going rules allow, and the agent asks it only when it can't tell which task to continue.

Failure modes and guardrails

FailureGuardrail
Write collisionsEach agent has one file and writes it atomically. Agents don't edit each other's files, except to mark a file whose process has exited or when I ask.
Lost contextThe checkpoint field is written so another session can resume from it.
Parallel edits to the same filesEach split child gets its own worktree and branch. The default is one session per initiative.
Status files committed to the repoThe folder goes into git's local exclude list.
A stale censusThe census marks sessions with no live process as not live, regardless of their last report.

Tradeoffs and alternatives

  • The rules started with one shared status file and moved to one file per agent.
  • A central server or database would offer more features, but it's another service to keep running, and every harness would need a client. Plain files work in every harness.
  • Asking each session for status costs that session context and time. Reading a file costs the session nothing.

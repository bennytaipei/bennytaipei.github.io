How my coding-agent kit fits together

Three parts: a devkit that runs the development loop, a knowledge base the agents read from, and a small set of harness-agnostic tools. This page covers how they connect, not what's inside them.

System overview

flowchart TD
  Dev[Engineer] --> Harness[Coding-agent harness]
  Harness --> Kit[Devkit plugin]
  Kit --> Flow[Task workflows]
  Flow --> Agents[Role agents: design, develop, test, review]
  Agents --> PR[Pull request on a product repo]
  PR --> Review[Automated PR review]
  Review -->|findings| Agents
  KB[(Shared knowledge base)] -->|context| Kit
  Tools[Harness-agnostic tools] --> Harness

The devkit is a plugin for a coding-agent harness. It turns a ticket into small spec stories, then runs workflows where separate agents handle design, development, testing, and PR creation. Each step's output is checked before the next starts.

Every PR goes through automated review: a code-review agent and a security-review agent comment on it, and a review loop feeds their findings back to the developer agent until the PR is clean or a person steps in.

Updating is one command. It pulls the newest plugin and the newest knowledge base, then reseeds each project's agent context, so every engineer runs the same version.

Knowledge base sync

flowchart TD
  A[Decision captured locally] --> B[Conflict check against shared KB]
  B --> C[Synced into local agent rules]
  C --> D[PR to shared KB]
  D --> E[Team review and merge]
  E --> F[Devkit update pulls KB]
  F --> G[Seeded into project agent context]
  G -.next decision.-> A

Upstream: when an engineer settles something worth keeping, such as a build quirk or a review rule, a capture step writes it to a personal knowledge base, checks it against the shared one for conflicts, and opens a PR. Teammates review each entry like code.

Downstream: after merge, the devkit's update step pulls the shared knowledge base and copies it into each project's agent context. The boundary is strict. One plugin owns every write to the shared knowledge base, and the devkit only reads.

Tools and the human handoff

sequenceDiagram
  participant Ag as Agent
  participant Br as Browser tool
  participant Me as Me
  Ag->>Br: navigate(url)
  Br-->>Ag: page loaded
  Ag->>Br: read() or screenshot()
  Br-->>Ag: login wall
  Ag->>Br: handoff(reason, timeout)
  Br->>Me: notify and share live browser
  Me->>Br: sign in, then done
  Br-->>Ag: status: done / timeout / cancelled
  Ag->>Br: read()

The tools are described as manifests, not tied to one harness. Each tool has typed inputs and outputs, a stated side effect, named error codes, and the names (never the values) of the credentials it needs. A checker validates every manifest against one schema, and versions follow semver.

The browser namespace has four tools: navigate, read, screenshot, and handoff. Handoff is a single blocking call. It shares the live browser, notifies me, waits until I finish or the timeout passes, and always ends the share itself. The agent gets back done, timeout, or cancelled, with no separate start or stop step to forget.

Session control for local agents is covered in local-agent-mcp.

Keep Going: a portable anti-stall design for coding agents

One principles file that every coding-agent harness loads as global instructions. It helps agents finish work without being prompted, and limits the open loops the person supervising them has to track.

Built in 2026 · Part of my AI developer tooling work

The problem

Coding agents are good at individual steps and bad at finishing. The common failure is not a wrong answer; it is a stop. The agent writes a plan, fetches one page, prints a status table, and then waits with "want me to (1)… or (2)…?" The human has to come back and poke it: "go on", "check git too", "you missed the other page". Each poke is cheap alone but costly in aggregate.

The second problem appears once agents do keep going: overload. Several live sessions, each able to ask a question, each with a half-finished claim of "done", turn the human into a full-time supervisor. More parallel agents did not mean less work for the person; it meant more open loops to remember.

Keep Going is one principles file, loaded as global instructions by every harness, that addresses both: finish the work without being poked, and don't multiply the human's open loops while doing it.

Design goals

  • Portable. Principles only. No product names, tool paths, or slash commands. Harness specifics live in a separate install map.
  • Overrides the wait bias, not the safety rules. It never weakens secrets, confidentiality, destructive git, the work/personal boundary, paid fan-out, or the WIP caps.
  • Measured. Every rule traces back to a pattern seen in real transcripts, not to taste.

The rules, by section

1. Anti-stall and continue-signals

Waiting after a plan or partial fetch is a failure. State assumptions in one line and continue. Only a short list of things justifies a blocking question: secrets, destructive git, work/personal boundary, spend or fan-out, or two equally costly forks. "Which page?" and "should I check git too?" are not blocking: pick the obvious source, log it, keep going.

The section's key idea is the continue-signal: events that look like a reason to stop but actually mean "you stopped too early". Examples:

  • A burst of short follow-ups from the user after a pause.
  • A status dump that ends while the checkpoint still lists non-human next steps (a "silent wait").
  • A mid-session redirect or correction: absorb it into the checkpoint and carry on, rather than replying "got it, say go".
  • A causal story: write what would falsify it and run the cheapest test before filing tickets.
  • A reviewer's severity label, or a reopen after a claimed done.
  • A defect found along the way: file a durable ticket with a repro rather than dismissing it as out of scope.

Two later additions target specific thrash patterns. After a tool or API failure on a field name, payload shape, or line target, read the schema or a known-good call before retrying instead of guessing again. During live design iteration, after the second acceptance-changing steer, freeze a short acceptance checklist on disk and work against it without pausing for approval after every tweak.

"Done" means the artifacts on the branch or remote match the claim, not that the session says so. For visual work, done requires actually rendering the UI and checking a screenshot against the criteria.

2. The epic research loop

When the user names a tracker item or a rough outcome, the agent runs a fixed chain without asking between hops: recall prior sessions → field-filtered tracker read → linked design docs → git history and code → rewrite the checkpoint → synthesize (and save durable decisions to the knowledge base) → produce the next artifact. Each hop writes a note to disk. Loaded context is a starting point, not a waiting room.

3. Disk is the memory

Conversations get compacted; files survive. Transcript mining showed that long sessions that shipped kept rewriting a plan or checkpoint file, while stalled ones kept the plan in chat. So every session keeps a small checkpoint: objective, current state, decisions, files changed, commands that worked or failed, next action, unresolved items. On resume, read it and verify against the filesystem before doing anything.

Early-flush triggers were tightened over time. The checkpoint must exist before the second mid-flight steer, not after compaction or a human status poke. A long session whose plan lives only in chat is a stall even if tools are still running.

4. Overflow is a continue-signal

Context usually dies from worker transcript dumps and large tracker-edit payloads, not the user prompt. Workers return 400–600 word summaries and write result files; the main session reads files, never raw worker logs. Large connector writes go in a fresh, empty session. Flush triggers: the second real user poke with no checkpoint yet, or a chat history over about 1 MB with none. On "prompt too long": flush, start a successor session, resume from the file. Overflow is never a reason to stop.

5. Auto-invoke

If a prompt mentions an epic, story, or issue key, the agent fires recall, tracker/wiki reads, git history, the checkpoint write, and knowledge ingest without waiting for a slash command. It never auto-fires deploys, notification toys, or paid multi-agent fan-out. Git is the progress bar: commit, push, and comment as you go.

6. Subagents vs main

Read-only research belongs to background workers; the main context handles decisions and implementation. Workers write files and the parent reads them. Writes to external systems stay with the parent when the harness would block them in workers. No fire-and-forget: check worker output, and resume an expired worker by id rather than starting over.

7. Hard stops

Secrets, confidentiality, force-push or hard reset, the work/personal boundary, paid or multi-agent spend, and two equally costly design forks. Everything else: assume, log, continue.

8. Tip-trust: done that scales under light supervision

When a human can't check every turn, "trustworthy" has to mean something more specific than the builder's self-report. The vocabulary:

  • Source of truth: the brief or reference that defines acceptance, gathered before building.
  • Acceptance checklist: frozen rows, one criterion each.
  • Tip artifact: concrete evidence (path, screenshot, URL, PR tip) that actually shows the claim.
  • Tip pack / tip-claim: one claim mapping every row to an artifact.
  • Tip-PASS / tip-HOLD: the verifier's verdict. Only PASS unlocks done, push, or the next epic.
  • Builder ≠ verifier: the builder never passes its own work.
  • GUI VERIFY: for look-and-feel work, a live render plus a screenshot scrub against the criteria. Curl, a deploy hash, or a passing build doesn't count. If display or auth blocks it, done is marked provisional.

Rules: resolve ambiguity into checklist rows before building; reject claims the evidence doesn't visibly show; one checklist and one comparison at the end, not continuous dual checking; any acceptance change resets the tip and needs one consolidated re-claim; a HOLD is a continue-signal with named gaps, not an invitation to drip one-row claims.

9. WIP and mental load

Every new session, agent wake, or verification request costs the human attention until it passes or is explicitly parked.

  • WIP cap: at most two active coding sessions plus one verifier track. Park one before opening a third.
  • Silent spillover: a defect found mid-epic becomes a ticket plus a checkpoint row, and the parent stays on its objective. A silent child session then drives that ticket to its farthest non-human end (implement, test, open a PR, attach evidence), using the ticket as its only status channel: comments and status moves, never chat pokes or menus. Human-only gates become ticket blockers and the child stops cleanly. Silent doesn't mean unsupervised: the child follows the same checkpoint and tip-trust rules.
  • No curiosity branches mid-day. One ticket-scoped branch per spillover ticket is fine; a pile of anonymous branches is not.
  • One tip pack per epic per day at most, with no status-only wakes.
  • An overflow successor replaces its predecessor. It doesn't run alongside it.
  • Done for the human means fewer open loops: a pass, a parked checkpoint with no non-human steps left, or an explicit parked row.

The reasoning: spawning a chatty agent per issue is the same supervision cost as opening that session yourself. Offload only happens when the extra work is invisible until it needs a human decision.

How it evolved

  • Late August: the first version was mined from about 1,150 coding-agent sessions. Sessions that shipped were long, rewrote a plan file, and ended on an artifact. Stalls were tiny (about 3 user turns), wrote nothing, and ended on a menu. Sections 1–7 came from that contrast.
  • Early September: tip-trust (§8) and WIP/mental load (§9) were added as multiple parallel sessions became the norm. Rules added: minimize mid-day branches, prefer deeper checkpoints over more subagents, and later the silent spillover session with the ticket as its bus.
  • Daily scoring since then: a weekday morning job counted "pokes" (user nudges an agent could have avoided) per session in the previous day's transcripts and made one small, generic patch when the count regressed. Patterns it caught:
  • silent waits after status dumps (Sep 9)
  • field-name thrash and live design drip (Sep 10)
  • a 42-poke design session with no checkpoint on disk, which led to freezing the checklist on disk after the second redirect (Sep 12)
  • large chats with no checkpoint, which moved the flush trigger from "third steer / over 1 MB" to "second steer / second poke" (Sep 15–16)

Short sessions returned to roughly zero pokes once the silent-wait rule landed. - Mid-September: one harness kept regressing while others improved. The cause was a stale embedded copy of the file, not the rules (see below).

How each harness loads it

There are two files: the principles file, which agents load, and an install map for humans that holds harness paths, kick commands, and provenance.

  • OMP: the global AGENTS.md @-includes the live principles file, so edits take effect in the next fresh session. Don't use OMP's SYSTEM.md, which replaces the default template; APPEND_SYSTEM.md is the fallback.
  • Grok Build: ~/.grok/AGENTS.md holds an embedded copy (within the roughly 10k-character cap). It must be refreshed whenever the principles change. A three-week-old paste is why this harness lagged.
  • Claude Code: principles are pasted above core behaviors in the shared global instructions file (shared.md) under a "Keep going research workflow" heading. The older "stop and wait for resolution" rule explicitly doesn't apply to research.
  • Cursor: an always-applied rule file (.cursor/rules/keep-going.mdc) points at the principles.

Silent spillover children run as non-interactive sessions with the same short prompt in each harness: a fresh print-mode session in the ticket's worktree, never a resume of the active session.

Already-open resumed sessions keep the old text, so changes only take effect in fresh sessions.

Takeaways

  1. Treat "the agent stopped" as a bug with named causes, and give each cause a continue-signal.
  2. Keep the plan on disk, not in chat.
  3. Separate builder from verifier, and require evidence that shows the claim.
  4. Cap the open loops a person sees. Offload by making extra work silent, not by adding more chats.
  5. Tune with data: count pokes, patch generically, re-measure.

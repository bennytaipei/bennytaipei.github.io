An AI pull-request reviewer that blocks on what matters

A reusable CI pipeline that reviews every pull request in focused passes (security, reliability, compatibility, compliance), remembers what it already said, and blocks merges only on high and critical findings.

Built in 2026 · Part of my AI developer tooling work

Problem and constraints

A network-security product has to meet compliance programs such as FedRAMP, ISMAP, and PCI DSS. Human reviewers couldn't check every pull request against all of that, and generic AI review bots produce noise. Noise matters: if a bot repeats the same finding on every push, developers stop reading it.

  • Review had to run on every pull request, in many repos, with almost no setup per repo.
  • It had to call a corporate LLM endpoint, with keys held as CI secrets.
  • Teams needed to try it in advisory mode first and switch to blocking later.
  • Findings must never apply to code that has already moved on, for example after a force push.

Architecture

flowchart LR
  C[Product repo: contract + thin workflow] --> U7[Orchestrator]
  U7 --> U2[Risk classifier]
  U7 --> U3[Freshness check]
  U7 --> U4[AI review engine]
  U7 --> U5[Comment writer + memory]
  U7 --> U6[Check run]

I split the reviewer into small units with clear boundaries. Each one has a single job and its own tests. A product repo adopts it with two files: a contract that names its risky paths, languages, and mode, and a short workflow that calls the shared reusable workflow. A later unit runs the same engine as a GitHub App on webhooks, for orgs where reusable workflows don't fit. Two more units sit beside the pipeline: an on-demand full-repo compliance scan that reuses the review prompts, and a fix-PR creator that needs human approval.

Control and logic flow

flowchart TD
  A([PR opened or updated]) --> B[Load contract]
  B --> C{Kill switch?}
  C -->|disabled| Z1([Exit])
  C -->|advisory or blocking| D[Classify changed files]
  D --> E{All low risk?}
  E -->|yes| Z2([Exit: nothing to review])
  E -->|no| F{Head SHA still current?}
  F -->|no, force push| Z3([Abort stale review])
  F -->|yes| G[Start check run]
  G --> H[Pass 1: security]
  H --> I[Pass 2: reliability]
  I --> J[Pass 3: compatibility]
  J --> K[Compliance pass]
  K --> L{Findings?}
  L -->|no| M([Check passes])
  L -->|yes| N[Drop repeats, post summary and findings]
  N --> O{Blocking mode and any high or critical?}
  O -->|yes| P([Check fails: merge blocked])
  O -->|no| Q([Check passes: advisory])

Each pass has its own prompt and looks at one concern. One prompt that covers everything mixes the domains: security notes leak into style comments, and the model spreads its attention thin. Separate passes cost more calls, but each finding is sharper and easier to trust.

Three early exits keep cost and noise down. The kill switch turns the agent off per repo without a code change. The risk classifier skips pull requests that touch only low-risk paths. The freshness check aborts if the head commit moved during the run, so a review never lands on code it didn't read.

Data flow: review memory

sequenceDiagram
  participant O as Orchestrator
  participant G as PR comments
  participant H as Compare API
  participant W as Comment writer
  O->>G: read earlier agent comments
  G-->>O: reviewed SHA + finding fingerprints
  O->>H: files changed since that SHA
  H-->>O: changed-file set
  O->>W: new findings
  W->>W: same fingerprint + file unchanged = collapse as repeat
  W->>W: fingerprint dismissed by developer = suppress
  W->>G: replace old agent comment with one fresh summary

The reviewer keeps no database. Its memory lives in the pull request itself. Every agent comment carries hidden markers with the reviewed commit and a fingerprint for each finding. On the next run, the writer reads them back and asks the compare API which files changed since then. A finding with the same fingerprint in an unchanged file is a repeat, so it gets collapsed rather than posted again. A developer can dismiss a fingerprint with a marker in a comment, and that suppression sticks. Old agent comments are deleted and replaced, so the thread always shows one current summary.

Failure modes and guardrails

  • Bad or noisy rollout: advisory mode first. The kill switch is in the contract.
  • Stale review after a force push: the SHA check aborts the run.
  • Repeated findings: fingerprints, the changed-since check, and developer dismissals.
  • Over-blocking: only high and critical findings fail the check, and only in blocking mode.
  • Large repos for compliance scans: the on-demand full-repo scan filters by language and skip paths, splits files into LLM-sized batches, removes duplicate findings, and files one issue as the result.
  • Automated fixes: a separate unit can open a fix PR against the feature branch, but a human must approve it. It never pushes to the author's branch.
  • Secrets: the endpoint, key, and checkout token are CI secrets, referenced by name only.

Tradeoffs and alternatives I rejected

  • A database for review history. More flexible, but it's one more service to run and secure. PR comments are already scoped, audited, and visible to the developer.
  • One combined review prompt. Cheaper, but noisier and harder to tune.
  • Blocking from day one. Fastest path to enforcement, but also the fastest way to lose developer trust.
  • Auto-pushing fixes. Rejected. Fix PRs are separate and need human approval.

What I'd do next

  • Label a sample of findings as true or false positives, so each pass's precision can be tracked over time.
  • Feed developer dismissals back as prompt examples for each repo.
  • Link findings to compliance control IDs so audit evidence comes out of normal review.

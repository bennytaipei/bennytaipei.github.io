AI pull-request reviewer

I built a reusable CI pipeline that reviews pull requests in separate security, reliability, compatibility, and compliance passes. It suppresses findings it already reported and blocks merges only on high and critical findings.

Built in 2026 · Part of my AI developer tooling work

Problem and constraints

A network-security product has to meet compliance programs such as FedRAMP, ISMAP, and PCI DSS. Human reviewers couldn't check every pull request against all of them. When a review bot repeats the same finding on every push, developers stop reading its comments.

  • Review had to run on every pull request, in many repos, with little setup per repo.
  • It had to call a corporate LLM endpoint, with keys stored as CI secrets.
  • Teams needed to run it in advisory mode first and switch to blocking later.
  • Findings must not apply to code that has changed since the review started, for example after a force push.

Architecture

flowchart LR
  C[Product repo: contract + thin workflow] --> U7[Orchestrator]
  U7 --> U2[Risk classifier]
  U7 --> U3[Freshness check]
  U7 --> U4[AI review engine]
  U7 --> U5[Comment writer + memory]
  U7 --> U6[Check run]

I split the reviewer into small units. Each unit has one job and its own tests. A product repo adopts it with two files: a contract that names its risky paths, languages, and mode, and a short workflow that calls the shared reusable workflow. Another unit runs the same engine as a GitHub App on webhooks, for orgs where reusable workflows don't fit. Two more units sit beside the pipeline. One is an on-demand full-repo compliance scan that reuses the review prompts. The other is a fix-PR creator that needs human approval.

Control flow

flowchart TD
  A([PR opened or updated]) --> B[Load contract]
  B --> C{Kill switch?}
  C -->|disabled| Z1([Exit])
  C -->|advisory or blocking| D[Classify changed files]
  D --> E{All low risk?}
  E -->|yes| Z2([Exit: nothing to review])
  E -->|no| F{Head SHA still current?}
  F -->|no, force push| Z3([Abort stale review])
  F -->|yes| G[Start check run]
  G --> H[Pass 1: security]
  H --> I[Pass 2: reliability]
  I --> J[Pass 3: compatibility]
  J --> K[Compliance pass]
  K --> L{Findings?}
  L -->|no| M([Check passes])
  L -->|yes| N[Drop repeats, post summary and findings]
  N --> O{Blocking mode and any high or critical?}
  O -->|yes| P([Check fails: merge blocked])
  O -->|no| Q([Check passes: advisory])

Each pass has its own prompt and covers one concern. A single prompt for every concern tends to mix them, for example security notes in style comments. Separate passes cost more LLM calls and make each finding easier to check and tune.

Three early exits limit cost and noise. The kill switch in the contract turns the agent off for a repo without a code change. The risk classifier skips pull requests that touch only low-risk paths. The freshness check aborts if the head commit moved during the run.

Review history

sequenceDiagram
  participant O as Orchestrator
  participant G as PR comments
  participant H as Compare API
  participant W as Comment writer
  O->>G: read earlier agent comments
  G-->>O: reviewed SHA + finding fingerprints
  O->>H: files changed since that SHA
  H-->>O: changed-file set
  O->>W: new findings
  W->>W: same fingerprint + file unchanged = collapse as repeat
  W->>W: fingerprint dismissed by developer = suppress
  W->>G: replace old agent comment with one fresh summary

The reviewer stores its history in the pull request instead of a database. Every agent comment carries hidden markers with the reviewed commit and a fingerprint for each finding. On the next run, the writer reads those markers and asks the compare API which files changed since that commit. A finding with the same fingerprint in an unchanged file is a repeat, and the writer collapses it. A developer can dismiss a fingerprint by adding a marker in a comment, and that dismissal persists. The writer deletes old agent comments and posts one current summary.

Failure modes and guardrails

FailureGuardrail
A noisy rolloutTeams start in advisory mode, and the contract has a kill switch.
A stale review after a force pushThe SHA check aborts the run.
Repeated findingsFingerprints, the changed-since check, and developer dismissals.
Blocking too muchOnly high and critical findings fail the check, and only in blocking mode.
Large repos in compliance scansThe scan filters by language and skip paths, splits files into LLM-sized batches, removes duplicate findings, and files one issue.
Unwanted automated changesThe fix-PR unit opens a separate PR against the feature branch and needs human approval. It doesn't push to the author's branch.
Secret exposureThe endpoint, key, and checkout token are CI secrets, referenced by name only.

Tradeoffs and alternatives

  • A database for review history would be more flexible, but it's another service to run and secure. PR comments are already scoped to the PR, audited, and visible to the developer.
  • One combined review prompt would be cheaper, but noisier and harder to tune.
  • Blocking from the start would enforce rules sooner, at the cost of developer trust while the prompts are still being tuned.
  • I didn't allow auto-pushed fixes. Fix PRs are separate and need human approval.

Next steps

  • Use developer dismissals as prompt examples for each repo.
  • Map findings to compliance control IDs, so review output can serve as audit evidence.
